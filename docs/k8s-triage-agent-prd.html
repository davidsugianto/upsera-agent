k8s-triage-agent: an AI SRE agent for Kubernetes operations

An off-cluster agent that turns a Datadog monitor alert into an evidence-backed root cause in about a minute and a half (p50), and proposes fixes that run only through a typed action catalog, a policy gate, and human approval.

1Summary

Operating production Kubernetes means reading pod states, events, rollout history, metrics, and logs across several tools before anyone can say why something broke. This project builds an AI SRE agent that does that legwork automatically, explains its conclusion with linked evidence, and offers a safe next action.

The design follows the six evaluation criteria from Atmosly's article How to Choose an AI SRE Agent for Kubernetes Operations (Aug 2026): Kubernetes-native understanding, multi-signal incident investigation, controlled remediation, toolchain integration, observability context, and security governance. Here those criteria are treated as build requirements instead of a buying checklist. Appendix A maps each of the article's buyer questions to the section that answers it.

Scope. upsera-agent is the project and GitHub repository; k8s-triage-agent is its first agent and the only one this PRD specifies. Shared parts (LLM providers, the Datadog client, read-only tools, redaction, policy, audit) sit in agent-neutral packages so later agents can reuse them, but no other agent is designed here. The agent runs outside the clusters it diagnoses (ADR 0002), so it stays available during the incidents it exists for. The LLM is a configuration choice (Anthropic, OpenAI, Gemini, or any OpenAI-compatible endpoint), not a dependency.

Datadog-native. Alerts come from Datadog monitors, and telemetry reaches Datadog through the OpenTelemetry Collector and custom exporters (and the Datadog Agent, if deployed; see open questions). Datadog is therefore the only alert and telemetry source: there is no Prometheus, Alertmanager, or SigNoz. The agent reads live cluster state from the Kubernetes API and everything else from Datadog. The investigation method comes from the team's existing SRE skills (datadog-investigate, k8s-triage, sre-incident-response), turned into a service with budgets, policy, and evals; section 5 maps each step of today's workflow to a component. It does not try to replace Datadog's own Bits AI SRE. What it adds is in-cluster, policy-gated remediation, an open eval suite, and control over prompts and the data path.

Design stance. Rules first, LLM second. Deterministic detectors catch known failure signatures cheaply; the LLM handles correlation and explanation. The LLM never holds write credentials: it can only propose actions from a fixed catalog, and a separate policy-gated executor carries them out.

2Problem and goals

Problem

  • Alerts say what is wrong (high error rate, pod restarting) but rarely why. The on-call engineer rebuilds context by hand from kubectl, Datadog dashboards, logs and traces, and the deploy history.
  • Most incidents trace back to a recent change: a rollout, a config edit, a scaling event. Linking the change to the symptom is slow and error-prone at 3 a.m.
  • Generic AI assistants can answer questions about a cluster but don't model Kubernetes relationships, cite evidence, or respect production change controls.

Goals

  • Cut time from alert to probable root cause to under 90 seconds (p50).
  • Back every conclusion with inspectable evidence.
  • Offer remediation that is safe by default, with human control over what runs.
  • Fit the existing GKE stack: Datadog monitors and telemetry, the OpenTelemetry Collector with custom exporters, Slack, and Argo CD and GitHub Actions where used.
  • Ship as a well-documented open source repo with a reproducible eval suite.

Non-goals for v1

  • Replacing monitoring or alerting. The agent consumes Datadog monitor alerts; it never creates, edits, mutes, or resolves monitors, dashboards, or Datadog incidents.
  • A free-form chatbot with cluster-admin access.
  • Other agents in upsera-agent (cost review, security, and so on). Shared packages stay agent-neutral, but only k8s-triage-agent is in scope.
  • Fixing application code. The agent can point at a bad commit but won't write the patch.
  • Non-Kubernetes infrastructure (VMs, managed databases) beyond reading their metrics.

5Architecture

The agent is the team's current incident workflow turned into a service. This section starts from that workflow, maps each of its steps to a component, and then shows the target design.

Today: the skill-driven workflow

Today the on-call engineer opens Claude Code and runs /sre-incident-response <datadog-link>. The skill acts as incident coordinator, not as an investigator: it opens a timestamped log, proposes a severity, and hands the analysis to whichever investigation skills match the input (a Datadog link goes to datadog-investigate, a named workload to k8s-triage, both in parallel). It then records their answers, keeps a synthesis, and drafts mitigation options and status updates for the engineer, who stays the incident commander and makes every change.

What already works

  • Read-only by construction. Neither the coordinator nor the investigators change production; writes come back for approval.
  • Investigators are a roster. They are picked by input and run in parallel. Adding one means adding a row.
  • A timeline you can trust. Times come from a script, answers are saved verbatim, and the coordinator never raises an investigator's confidence.
  • Conflicts stay visible. The synthesis gives one row per source, says what each source cannot see, and names the next evidence needed.
  • The postmortem comes from the same log. It is blameless and keeps unknowns marked as unknown.

What is still manual

  • Trigger. Someone has to notice the alert and paste the link. The agent takes the monitor webhook (INT-1).
  • State. Incident state lives in Markdown on one laptop, and handover happens only through the Slack thread. The agent keeps a Postgres incident store and an API.
  • Identity. The skills run on the engineer's Datadog session and kubectl context. The agent uses read-only keys and a reader role per cluster (SEC-1).
  • Data handling. Keeping secrets out of the model depends on the model following the skills' rules. The agent redacts in the tool layer instead (SEC-2).
  • Measurement. Accuracy and time to RCA are not tracked. The agent adds evals and feedback (section 11, INV-7).
  • Fixes. Every fix is typed by hand. The agent adds the action catalog and policy gate (section 7).

Each step of the current workflow becomes a component or requirement of the agent. The method stays the same; the trigger, the storage, the identity, and the write path change.

Target architecture

Four stages: ingest signals, reason over them with read-only tools, decide on an action through policy, and act with a narrowly scoped identity. Reasoning is split the same way as in the skills: an Incident Coordinator routes, records, and synthesizes, and investigators find the cause. The read path and the write path never share credentials.

Deployment topology

The agent runs off-cluster (ADR 0002): on a management cluster or a VM, outside the clusters it diagnoses. It reaches each target cluster remotely with a per-cluster identity, listed in a cluster registry with namespace allow and deny lists: a Google identity bound by the reader ClusterRole through Workload Identity on GKE, and a ServiceAccount token in dev. No admin kubeconfig is stored. Phases 0 to 4 run as a single Helm release on the management side. Phase 5 adds multi-cluster scale through the registry rather than agents inside each cluster. The Datadog keys live only on the management side, and the executor uses its own identity per target. Where RemediationRequest records live now that the agent is remote is an open decision (ADR 0005, Phase 4). Remote informers watch over the network, so watch volume is something to measure in Phase 3.

6Investigation loop

Each incident moves through a fixed sequence. Known signatures can skip straight to the report; anything unclear loops through gather and hypothesize until confidence is high enough or the budget runs out.

Method, taken from the team's skills

  • Scope from the alert. The monitor's query, threshold, tags, and transition time set T0 and a pre-incident baseline window. The problem statement says what the monitor actually measures.
  • Hypotheses, then probes. Three to six specific, falsifiable hypotheses across layers (change, capacity, dependency, config, node, traffic). The planner writes the probes, executors run them, rounds are capped.
  • Live cluster first for workload questions. Events before logs, the owner chain, and rollout history, read from the Kubernetes API. Attaching a debug container is a write and is out of scope for v1.
  • Confidence scale. High: cause, timing, and mechanism are all shown. Medium: one of the three is not shown. Low: the cause fits but nothing tested confirms it. A single correlated deploy with no mechanism is medium at most.
  • Closing chain. Trigger, mechanism, why it crossed the monitor threshold, recovery; then ruled out, still open, contributing factors, and confidence. An unproven link is named as open, never filled in with a guess.

Guardrails on every write

  • Dry-run first. Server-side dry-run must succeed before the real request.
  • Verify after. Each action declares a check, for example "ready replicas back to desired within 5 minutes". On failure the executor reverts if it can and escalates.
  • Blast radius. At most 1 action per workload per 15 minutes and 3 per cluster per hour.
  • Kill switch. A flag in the agent's own configuration on the management side (hot-reloaded; never a ConfigMap in a target cluster, which the reader role cannot read) or /triage freeze in Slack drops every mode to L0 immediately. A subPath config mount never refreshes, so REM-5 must mount the config directory (or a separate flag file) and re-read it; the Phase 0 chart restarts the pod on a config change instead.
  • Datadog stays read-only. Muting a monitor, editing a threshold, or resolving a Datadog incident is not in the catalog. The agent can propose a monitor change as text for its owner.
  • GitOps respect. Workloads managed by Argo CD get changes through Git, so the next sync does not undo the fix.

10Security and governance

Access

  • Reader ClusterRole: get, list, watch on workloads, nodes, events, services, endpointslices, networkpolicies, HPA, PDB, PVC; get on pods/log. No Secrets.
  • Executor Role: bound per namespace that opted in. Only the verbs the catalog needs: delete pods, patch deployments and scale. Cordon, if enabled, needs its own ClusterRole limited to patching nodes.
  • GCP access through Workload Identity. The only long-lived credentials are the read-only Datadog keys and the Slack tokens, kept in Secret Manager and never exposed to the executor or the LLM.

Data handling

  • Redaction runs inside the tool layer, before data reaches the investigator. Patterns cover tokens, keys, JWTs, emails, and all env values. They apply equally to Datadog log lines, span attributes, and monitor messages.
  • Only redacted excerpts go to the LLM. Raw logs stay in Datadog.
  • Self-hosted LLM mode keeps prompts and excerpts inside your own network; Datadog reads still go to your Datadog site.

Prompt injection

  • Tool output, including Datadog monitor messages, log lines, span attributes, and event text, is wrapped and labelled as untrusted data in the prompt.
  • A log line saying "delete the namespace" can at worst produce a proposal; the catalog has no such action and the gate would deny it.
  • The eval suite includes injection scenarios (section 11).

How the suite runs

  • Kubernetes-only scenarios (1 to 6) run on kind with the Phase 1 tools. Scenario 6 (disk pressure) is hard to reproduce on kind and may be lab-only or replayed.
  • Datadog-dependent scenarios (7 to 10) and every alert-driven run use recorded Datadog responses in PR CI, and the live GKE lab with the Datadog Agent and OpenTelemetry Collector nightly. Scenario 9 needs a CNI that enforces NetworkPolicy.
  • Non-determinism. Each scenario runs three times and passes when at least two runs name the expected cause with valid evidence. Model and prompt versions are pinned per run.

14Open questions

  • Reference model: claude-sonnet-5-5 is the reference for evals and defaults (ADR 0003, accepted). Still open: do releases gate only on the reference, and what is the acceptable cost per investigation after the Phase 2 baseline?
  • Build the provider layer in-house (a thin interface and a few adapters) or adopt a Go LLM library? Resolved: in-house, per ADR 0003 (accepted).
  • Phase 1 evidence store: this draft assumes local SQLite with the final Evidence shape and Postgres from Phase 2. Resolved: local SQLite, per ADR 0004 (accepted).
  • Should non-GKE clusters (EKS, kind-only users) be a v1 target or community-contributed later?
  • How should Slack users map to Kubernetes identities: Google Groups, a static map, or OIDC claims?
  • Should every write go through Git, including pod deletes, for a single audit trail?
  • How does the agent authenticate to Datadog: API and application keys from Secret Manager, a service account, or the Datadog MCP with OAuth? This draft assumes keys for the service and MCP for the CLI.
  • Is the Datadog Agent deployed on the clusters, or does all telemetry arrive through the OpenTelemetry Collector and custom exporters? Are service, env, and version tags applied consistently, including on custom exporter metrics?
  • Are Argo CD and GitHub Actions both in use, or does Datadog already carry enough deploy and pipeline context?
  • Is there one Datadog org and site for all target clusters, or several?
  • Where do RemediationRequest records live now that the agent is off-cluster: a CRD on the management side with a cluster field, the database, or a CRD per target (ADR 0005, decided in Phase 4)?
  • Where does the agent run: a management GKE cluster, a VM, or another surface, and what diagnoses that host?
